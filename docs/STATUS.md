# Реализация и приёмка Check764P

## Проверенные факты

Полный оригинальный комплект XSD предоставлен пользователем. Контрольные суммы всех трёх файлов совпадают с ТЗ; основная схема успешно компилируется. Обезличенный XML из «Тесты.zip» прошёл оригинальную XSD: корень СообщОтказ_115ФЗ, версия 1.2, дата 19/10/2026, одна запись Раздел2, один участник.

Реализованы окно настройки колонок, автоматический запуск, адаптер, накопительная книга, архив XML, резервирование, два отчёта, повторная проверка, блокировка каталога и журнал восстановления. Версии 1.1/1.2, три раздела и все допустимые коды событий проверяются синтетическими XML, валидными по оригинальной XSD. Автоматические проверки включают повторы, конфликт содержимого, нарушение последовательности, закрытие отдельной записи, сохранение всех участников, незатирание базы при ошибке и восстановление транзакций.

Обезличенный рабочий пример прошёл полный запуск: 6 строк клиентов, 1 запись, оба отчёта, 0,109 с на Linux. Данные клиента не включены в репозиторий.

Локальные результаты тестов и встроенной самопроверки сохранены в `docs/validation`. Они относятся к Linux/Python 3.12 и не подтверждают запуск Windows EXE.

## Незавершённая приёмка и ограничения

* Первая Windows-сборка и самопроверка EXE подтверждены успешным запуском https://github.com/Muravlev-28/764p-proveryalka/actions/runs/41420197769 (коммит 4d8b598). Опубликован Check764P-Windows-x64, 18,3 МБ. GitHub API возвращает 403, но результат проверен через доступную страницу Actions. Второй запуск https://github.com/Muravlev-28/764p-proveryalka/actions/runs/41443089586 также успешен: самопроверка EXE включает настоящее окно приложения, автоматическую обработку и закрытие. Для последующих изменений проверяйте последний успешный запуск ветки codex/check764p-windows.
* Отдельная ручная проверка Windows 10 и Windows 11 не выполнена. CI `windows-latest` проверяет ту редакцию Windows, которую предоставит GitHub, и сохраняет её в результате самопроверки.
* Дополнительно проверен приложенный «Перечень xsd-схем_550p.doc»: он подтверждает назначение трёх XSD, но не содержит полного описания условности реквизитов. FORMAT_550P.doc и Change_550P.doc не предоставлены. Реализованы оригинальная XSD, условия из ТЗ и структурная согласованность блоков; полнота всех дополнительных текстовых условий официального формата ещё не подтверждена.
* Статус Указания № 7474-У, дата применения и наличие новых официальных форматов перед приёмкой не проверены: сайт ЦБ возвращал 403. Смена нормативного акта сама по себе не меняет поддерживаемый XML-профиль.
* Импорт поддерживает накопительную книгу Check764P с полными данными и соответствующим архивом. Произвольная legacy-книга другого формата требует отдельно определённого сопоставления полей; этот импорт не реализован.
* XML 1.1 проверен синтетически по приложенной XSD; рабочий обезличенный пример предоставлен только для версии 1.2.
* Нагрузочная проверка 20 000 клиентов / 100 000 записей / 300 000 участников выполняется отдельно, результат — `docs/validation/benchmark.json`. Первый полный замер: 878,780 с, пик RSS 10 499,4 МиБ (около 10,3 ГиБ), все 100 000 записей и 300 000 участников обработаны. Пользователь явно согласовал поставку с фактическим временем выше трёх минут. Повторный замер после оптимизации: **537,145 с (8 мин 57 с)**, пик RSS **10 738,8 МиБ (около 10,5 ГиБ)**; все данные и отчёты сформированы, сокращение времени около 39%. Результат сохранён отдельно; Linux-хост не является контрольным Windows-ПК с SSD из ТЗ.
* При огромном количестве кандидатов все результаты сохраняются. Время и размер результата могут быть значительными; top-k и скрытого отсечения нет.
* В настройках можно дополнительно сопоставить ID, ИНН, дату рождения и тип лица; стандартные заголовки также распознаются автоматически. Дополнительные реквизиты не скрывают кандидатов по имени; расхождения показываются отдельно.
* Длинные значения сохраняются без усечения на листах `ДлинныеЗначения` (отчёты) либо `Данные` (master). Источник XML, SHA и XPath сохранены в соседних колонках. При наличии происхождения длинное поле и SHA-256 содержат локальную гиперссылку на архивный XML, SHA и XPath; полный текст дополнительно сохранён в книге.
* При запуске без новых XML master не меняется; публикация пары отчётов также сопровождается журналом восстановления.

## Решения по неоднозначностям ТЗ

Приоритет имеет подробный раздел 8, предусматривающий расширенный поиск кандидатов. Раннее указание «только точное совпадение» ему противоречит. В отчётах текстовые совпадения никогда не объявляются автоматическим установлением тождества лиц. Поиск по частям ФИО допускает неоднозначный порядок и потому может давать слабые кандидаты по совпавшему слову; они сохраняются для ручной оценки.

## Восстановление

Работа ведётся под системной блокировкой `service/run.lock`. Файл остаётся после выхода, но блокировка освобождается ОС. Подготовленные книга и отчёты находятся внутри рабочей папки на том же диске. До замены базы проверяются SHA входных файлов, существующей базы и подготовленных результатов.

Журнал `service/transaction.json` содержит run_id, хеши базы до/после, отчётов и входов, пути резервной копии и этап. Смена master через `os.replace` — точка фиксации. При совпадении хеша с новой базой следующий запуск завершает публикацию отчётов. Если отчёт утрачен, проверенная резервная копия восстанавливается; уже опубликованные отчёты незавершённой операции убираются в service, чтобы не показывать ложный успех. Для первоначального создания восстанавливается отсутствие master, а новая книга сохраняется в service. При совпадении со старой базой транзакция отменяется. При неизвестном хеше автоматическое восстановление останавливается.

Обработанные XML фиксируются в одной master-книге вместе с записями и историей. Журналы завершённых транзакций сохраняются в `service/transactions`; история принятых событий не смешивается с историей запусков и пропусков.

Исходники версии 0.2.0: 54 автоматических теста. Внешние зависимости runtime и сборки закреплены в requirements*.txt.
